# ComplianceScan — Testing & Release Gate Specification

**Document:** `11_Testing_and_Release_Gate.md`  
**Version:** 1.1  
**Status:** Implementation Contract  
**Scope:** MVP / SIH’26 production-quality web application  
**Purpose:** Define how ComplianceScan is verified, hardened, and accepted for release.

---

# 1. Purpose

This document is the authoritative verification contract for ComplianceScan.

It answers:

> **How do we prove that the application works correctly before calling the MVP release-ready?**

Testing is not limited to whether individual buttons work.

ComplianceScan combines:

```text
Authentication
Evidence
Image Processing
OCR
Extraction
Applicability
Compliance Rules
Human Review
State Transitions
Reports
Repository
Search
Dashboard
Audit
```

Therefore testing must verify both:

1. **individual components**, and
2. **the complete stateful inspection journey**.

The application must be tested against the implemented MVP critical path first. The broader 25-stage target workflow remains a reference for future/full-system validation and must not be treated as a requirement to implement every target capability before MVP release.

---

# 2. Testing Philosophy

The primary testing principle is:

> **Test the behavior and invariants, not merely the implementation.**

A passing test suite is not sufficient if the system still permits a forbidden business outcome.

For example:

```text
API endpoint returns 200
```

does not prove:

```text
Inspector cannot finalize
```

The test must explicitly attempt the forbidden action.

Likewise:

```text
OCR endpoint works
```

does not prove:

```text
OCR failure cannot become compliance failure
```

The tests must exercise the failure path.

# 4. Test Environment

Minimum environments:

```text
Development
Test
Production-like / Demo
```

The test environment must not use real production secrets.

Recommended configuration:

```text
isolated test database
isolated test object/file storage
deterministic test users
deterministic test evidence
controlled rule snapshot
```

The deployed MVP must use persistent cloud-capable database and object/file storage. SQLite and local filesystem may be used for isolated local development/test runs only; they are not the deployed system of record.

Tests must not modify the developer's real inspection repository.

---

# 5. Test Data Principles

Use deterministic test data.

The test suite should include:

```text
valid package images
blurred images
dark images
rotated images
partial images
conflicting declarations
multiple MRP values
imported products
non-imported products
unknown applicability
```

Do not depend on live marketplace websites, live AI services, or external network behavior for the core automated test suite.

External integrations should have mocked/fake dependency tests plus a small controlled smoke test where appropriate.

# 8. Compliance-State Unit Tests

The result-state semantics must be tested explicitly.

For applicable checks:

```text
PROCESSING_FAILED
>
REQUIRES_REVIEW
>
POTENTIAL_NON_COMPLIANCE
>
INCOMPLETE
>
PASS
```

`NOT_APPLICABLE` is handled by applicability before this precedence.

Test examples:

```text
PASS + no conflict
→ PASS

Insufficient evidence
→ INCOMPLETE

Conflicting values
→ REQUIRES_REVIEW

Sufficient evidence of configured failure
→ POTENTIAL_NON_COMPLIANCE

Processing failure
→ PROCESSING_FAILED
```

The implementation must not collapse these states into a boolean.

# 22. State Machine Testing

The state machine is a critical release area.

Test every permitted transition.

```text
DRAFT
→ PROCESSING

PROCESSING
→ ANALYZED

PROCESSING
→ PROCESSING_FAILED

PROCESSING_FAILED
→ PROCESSING

ANALYZED
→ SUBMITTED

SUBMITTED
→ UNDER_REVIEW

UNDER_REVIEW
→ EVIDENCE_REQUESTED

EVIDENCE_REQUESTED
→ SUBMITTED

UNDER_REVIEW
→ FINALIZED
```

Also test every important forbidden transition.

Examples:

```text
FINALIZED → DRAFT
FINALIZED → PROCESSING
FINALIZED → SUBMITTED
```

must fail.

# 65. Regression Testing

Every bug fixed must receive a regression test when practical.

Example:

```text

```

# 66. Test Naming

Tests should describe behavior.

Good:

```text
test_inspector_cannot_finalize_inspection
test_ocr_failure_does_not_create_noncompliance_finding
test_finalized_inspection_cannot_be_modified
test_conflicting_mrp_requires_review
```

Bad:

```text
test_endpoint_7
test_helper
test_api
```

Behavior-oriented names make the suite useful as living documentation.

# 67. Test Isolation

Each test should start from a predictable state.

Recommended:

```text

```

Tests must not depend on execution order.

# 68. External Dependency Mocking


# 69. Compliance Regression Dataset

Maintain a small deterministic dataset representing the supported MVP scenarios.

Each case should contain:

```text

expected findings
expected review requirement
```

Whenever compliance logic changes, run the entire dataset.

This is especially important because compliance semantics must remain stable.

# 71. Test Coverage Philosophy

Code coverage is useful but is not the release criterion.

A high percentage does not guarantee correct compliance behavior.

Priority is:

```text
business invariants
>
state transitions
>
authorization
>
data integrity
>
critical processing
>
ordinary code coverage
```

Critical paths should have stronger tests than low-risk utility code.

```text
  ↓
```

```text
+

+

+
```

## Full-system validation

Future/full-solution capabilities may require additional validation for capabilities such as dynamic regulatory monitoring, rule-change workflows, advanced integrations, or other target architecture components. `MVP_BUILD_SCOPE.md` is the authority for what is currently release-blocking. The detailed specifications define the target system and contracts; their existence alone does not make every future capability an MVP release criterion.

# 80. Non-Negotiable Testing Invariants

1. **A passing UI test is not proof of backend authorization.**
2. **Every security boundary must be tested directly through the API.**
3. **Technical failure must never become compliance failure.**
4. **Insufficient evidence must never silently become absence.**
5. **NOT_OBSERVED must never silently become missing.**
6. **Conflicts must remain conflicts until resolved.**
7. **Unknown applicability must remain unknown until resolved.**
8. **Original evidence must remain immutable.**
9. **Evidence must never cross inspection boundaries.**
10. **Human corrections must preserve original observations.**
11. **Upstream corrections must invalidate affected downstream results.**
12. **Only an authorized Reviewer can finalize.**
13. **Concurrent finalization must have exactly one winner.**
14. **Finalization must be atomic.**
15. **Finalized inspections must be immutable.**
16. **Historical rule context must remain attached to historical inspections.**
17. **Reports are derived artifacts, not the source of truth.**
18. **A report failure must not undo a valid finalization.**
19. **Network retries must not duplicate consequential actions.**
20. **Dashboard/search failures must not masquerade as empty data.**
21. **Malformed AI output must never become authoritative.**
22. **Untrusted package/listing text must never override system instructions.**
23. **Database and filesystem consistency must be testable.**
24. **A release blocker cannot be waived merely because the demo UI works.**
25. **The final release decision must be based on tested invariants, not appearance.**
