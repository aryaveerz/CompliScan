# 1. Purpose

This document defines the domain model and domain semantics for ComplianceScan.

It establishes the meaning of:

- inspections
- products
- package context
- evidence
- observations
- OCR
- AI extraction
- declarations
- applicability
- assessments
- findings
- Inspector Verification
- Reviewer decisions
- evidence requests
- finalization
- rule snapshots
- audit history
- reports
- domain states
- domain invariants

The domain model separates:

```text
What was observed
        ↓
What the system interpreted
        ↓
What applies
        ↓
What the rules evaluate
        ↓
What the Inspector verified
        ↓
What the Reviewer decided
```

---

# 2. Domain Vision

ComplianceScan represents an inspection as an evidence-centered record.

The central domain chain is:

```text
Inspection
    ↓
Evidence
    ↓
Observation
    ↓
Declaration
    ↓
Applicability
    ↓
Assessment
    ↓
Finding
    ↓
Inspector Verification
    ↓
Reviewer Decision
    ↓
Final Snapshot
```

The system must preserve enough provenance to understand how a final result was reached.

---

# 3. Core Domain Principle

The domain follows:

> **AI finds → Evidence supports → Inspector verifies → Reviewer decides.**

The domain must not model AI output as equivalent to a final legal decision.

# 5. Domain Glossary

## 5.1 Inspection

A structured record representing one packaged-commodity inspection activity.

## 5.2 Product

The commodity/package being inspected.

## 5.3 Package Context

Context needed to understand the inspection and applicability of supported requirements.

## 5.4 Evidence

Information used to support observations and findings, primarily package images.

## 5.5 Primary Evidence

Original package evidence provided/captured for the inspection.

## 5.6 Supplemental Evidence

Additional evidence added later.

## 5.7 Derived Evidence

Artifacts generated from original evidence, such as crops or highlights.

## 5.8 Observation

A representation of something established or observed from evidence or manual inspection.

## 5.9 OCR Observation

Text/region information generated by OCR.

## 5.10 Declaration

A structured representation of a package declaration relevant to a supported requirement.

## 5.11 Applicability

Determination of whether a supported requirement applies in the inspection context.

## 5.12 Assessment

The system's evaluation of an applicable requirement against controlled rules.

## 5.13 Finding

An explainable record describing a potential issue, review condition, or relevant assessment supported by evidence.

## 5.14 Inspector Verification

Human verification/correction of the system's observations and assessments.

## 5.15 Reviewer Decision

Independent review/confirmation/correction/override performed by the Reviewer.

## 5.16 Evidence Request

A Reviewer request for additional information/evidence needed to establish a fact or condition.

## 5.17 Final Snapshot

Immutable historical representation of a finalized inspection.

## 5.18 Rule Snapshot

The controlled version of rules used to evaluate an inspection.

# 7. Inspection Identity

Each inspection must have a unique identifier.

Example:

```text
INS-00124
```

The identifier is a system identity, not a legal conclusion.

# 8. Inspection Context

An inspection may contain:

- inspection identifier
- date/time
- location/context
- Inspector
- product information
- import status
- package information
- relevant inspection metadata

Only fields required by the supported workflow should be mandatory.

# 9. Product Domain

The Product represents the packaged commodity under inspection.

Potential fields:

- product name
- common/generic product name
- manufacturer/packer/importer information
- product context
- package context
- imported status
- other supported attributes

Product information may be:

```text
System extracted
Inspector corrected
Manually observed
```

The source of each material value should remain traceable where applicable.

---

# 10. Import Status Domain

For the supported MVP applicability logic:

```text
YES
NO
UNKNOWN
```

Semantics:

### YES

Product is treated as imported for supported applicability logic.

### NO

Product is treated as not imported.

### UNKNOWN

Import status has not been established sufficiently.

---

# 11. Country of Origin Domain

Country of Origin is applicability-driven.

```text
Import Status = YES
        ↓
Country of Origin
APPLICABLE

Import Status = NO
        ↓
Country of Origin
NOT_APPLICABLE

Import Status = UNKNOWN
        ↓
Country of Origin
REVIEW / INCOMPLETE
```

The system must not assume universal applicability.

---

# 12. Evidence Domain

Evidence is a first-class domain object.

Each evidence item should have:

- Evidence ID
- inspection reference
- evidence type
- storage reference
- original/derived status
- timestamp
- provenance
- integrity hash
- metadata
- processing references

---

# 13. Evidence Types

## PRIMARY

Original package evidence supplied/captured for the inspection.

## SUPPLEMENTAL

Additional evidence provided later.

## DERIVED

Artifact derived from original evidence.

Examples:

```text
OCR crop
Highlight
Resized analysis image
Annotated evidence
```

Derived evidence must retain its source relationship.

---

# 14. Evidence Integrity

Each original evidence item should have a SHA-256 hash.

Domain meaning:

```text
Hash
 ↓
Change Detection / Integrity
```

Not:

```text
Hash
 ↓
Truth / Authenticity
```

The domain must not claim that hashing proves that an image is truthful.

---

# 15. Evidence Immutability

Original evidence must be immutable after acceptance.

If another image is supplied:

```text
New Image
   ↓
New Evidence ID
```

It must not overwrite the previous original evidence.

---

# 16. Evidence Provenance

A material observation should be traceable to evidence.

```text
Observation
    ↓
OCR Region / Manual Observation
    ↓
Evidence
```

A finding should be traceable through:

```text
Finding
   ↓
Assessment
   ↓
Declaration / Observation
   ↓
Evidence
```

---

# 17. Evidence Sufficiency

Evidence sufficiency answers:

> Is the available evidence sufficient to establish the required fact/condition for the supported workflow?

Possible domain outcomes:

```text
SUFFICIENT
INSUFFICIENT
UNCERTAIN
```

Evidence insufficiency is not itself a legal violation.

---

# 18. Adaptive Evidence

The domain does not require a fixed number of images.

Evidence requirements depend on:

- package complexity
- declaration coverage
- image quality
- visibility
- unresolved requirements

The system may request supplemental evidence when the existing set is insufficient.

---

# 19. Image Quality Domain

Image quality represents technical/visual usability of evidence.

Potential observations:

- blur
- brightness
- contrast
- orientation
- visibility
- coverage

Quality status must remain separate from compliance status.

---

# 20. OCR Domain

PaddleOCR is the current selected MVP OCR implementation.

An OCR run represents one OCR processing attempt.

It may contain:

- OCR Run ID
- evidence reference
- recognized text
- bounding boxes
- confidence
- processing timestamp
- processing status
- engine/version information

---

# 21. OCR Region

An OCR Region identifies text found in an evidence image.

Conceptually:

```text
OCR Region
├── Evidence
├── Text
├── Bounding Box
└── Confidence
```

The OCR region is a source observation, not a legal conclusion.

---

# 22. OCR Confidence

OCR confidence describes the OCR engine's confidence in the recognized text.

It does not represent:

- legal confidence
- compliance confidence
- evidence authenticity
- AI confidence

---

# 23. AI Run Domain

An AI Run represents one declaration-understanding attempt.

Current selected model:

> Gemini 2.5 Flash

An AI run should preserve:

- AI Run ID
- provider/model
- input references
- output status
- processing timestamp
- structured output
- error state where applicable

The AI run is part of provenance.

---

# 24. Declaration Extraction Domain

The AI layer converts OCR observations into structured declaration observations.

Conceptually:

```text
OCR
 ↓
AI Understanding
 ↓
Declaration Observation
```

AI may:

- extract
- normalize
- interpret context
- detect conflicts
- preserve uncertainty

AI may not make the final compliance decision.

---

# 25. Declaration Observation

A declaration observation should preserve:

- field
- value
- normalized value where applicable
- observation status
- AI extraction confidence where applicable
- source OCR regions
- source evidence
- provenance

---

# 26. Observation Status

Canonical statuses:

```text
OBSERVED
NOT_OBSERVED
UNCERTAIN
UNREADABLE
CONFLICTING
```

These statuses are semantically distinct.

---

# 27. OBSERVED

The declaration was sufficiently established from the available evidence or valid observation.

Example:

```text
MRP = ₹199
Status = OBSERVED
```

---

# 28. NOT_OBSERVED

The supported declaration was not established from available evidence.

Important:

> NOT_OBSERVED does not by itself prove that the declaration is legally absent.

---

# 29. UNCERTAIN

The system cannot reliably determine the declaration.

Causes may include:

- ambiguous text
- poor OCR
- ambiguous context
- insufficient semantic evidence

The value should not be silently promoted to a confirmed fact.

---

# 30. UNREADABLE

The relevant information may be present but cannot be reliably read.

This is distinct from:

```text
NOT_OBSERVED
```

and distinct from:

```text
POTENTIAL_NON_COMPLIANCE
```

---

# 31. CONFLICTING

Multiple materially different values have been observed.

Example:

```text
MRP
₹199 — Evidence A
₹179 — Evidence B

Status:
CONFLICTING
```

The system preserves the conflict rather than silently selecting one value.

Material conflicts generally route to:

> `REQUIRES_REVIEW`

---

# 32. Confidence Model

The domain keeps confidence dimensions separate:

```text
OCR Confidence
        ≠
AI Extraction Confidence
        ≠
Evidence Sufficiency
        ≠
Compliance Result
```

A confidence value must not be interpreted outside its intended meaning.

---

# 33. Manual Observation

An Inspector may record a manual observation.

Manual observations must be distinguishable from AI-generated observations.

Example:

```text
Source:
MANUAL_INSPECTOR_OBSERVATION

Actor:
Inspector

Evidence:
EVD-000002
```

---

# 34. No-Guessing Invariant

The domain must preserve:

> **No unsupported fact becomes an accepted declaration.**

Examples:

```text
Unreadable → UNREADABLE

Ambiguous → UNCERTAIN

Conflict → CONFLICTING

Missing evidence → INCOMPLETE / review
```

The model must not fill unsupported values from assumptions.

---

This represents the responsible-party declaration relevant to the supported scope.

The domain may preserve:

- observed text
- normalized party value
- role/type where established
- source evidence

# 37. Common / Generic Product Name Domain

Represents the common/generic product name declaration.

Preserve:

- observed value
- normalized value where appropriate
- source
- observation status

---

# 38. Net Quantity Domain

Represents:

```text
Quantity
+
Unit
```

Example:

```text
500 g
```

The domain should preserve the numeric quantity and standardized unit where successfully normalized.

Invalid or ambiguous units must remain reviewable.

---

# 39. Manufacture / Packing / Import Date Domain

Represents the supported month/year declaration.

The domain should preserve:

- observed date text
- normalized month/year where possible
- declaration context
- source
- observation status

Ambiguous date interpretation should remain uncertain.

---

# 40. MRP Domain

Represents the observed maximum retail price declaration within the supported MVP scope.

The domain should preserve:

- value
- currency
- tax-inclusion interpretation where established
- source
- observation status

MRP extraction and MRP compliance are separate domain concepts.

---

# 41. Consumer Care Domain

Represents supported consumer-care information.

The domain may preserve:

- phone/contact information
- address/contact text
- source
- observation status

The domain should not fabricate or normalize beyond evidence.

---

# 42. Applicability Domain

Applicability determines whether a requirement should be evaluated.

Conceptually:

```text
Inspection Context
      ↓
Applicability Decision
      ↓
Requirement
```

Possible semantic outcomes:

```text
APPLICABLE
NOT_APPLICABLE
UNKNOWN / REVIEW
```

---

# 43. Applicability Is Not Compliance

These are distinct:

```text
Applicability
    ↓
Should requirement be evaluated?

Compliance
    ↓
Does observed information satisfy requirement?
```

A requirement that is not applicable is not a passing compliance finding.

---

# 44. Requirement Domain

Each supported requirement should have a stable identity.

Example conceptual identifiers:

```text
LM-MVP-PARTY-001
LM-MVP-NAME-001
LM-MVP-QTY-001
LM-MVP-DATE-001
LM-MVP-MRP-001
LM-MVP-CARE-001
```

These identifiers are illustrative domain keys; the authoritative rule specification is in:

> `06_Compliance_Rules.md`

# 45. Assessment Domain

An Assessment represents evaluation of one requirement.

It should preserve:

- requirement
- applicability
- observed facts
- rule snapshot
- system result
- reason
- provenance
- calculation/recalculation history where relevant

---

# 46. Assessment Result Vocabulary

Canonical system results:

```text
PASS
POTENTIAL_NON_COMPLIANCE
REQUIRES_REVIEW
NOT_APPLICABLE
INCOMPLETE
PROCESSING_FAILED
```

These must remain distinct.

---

# 47. PASS

The supported requirement was evaluated and satisfied according to the controlled rule and available information.

---

# 48. POTENTIAL_NON_COMPLIANCE

The system identified an evidence-supported condition that appears inconsistent with the supported requirement.

This is not an autonomous legal judgment.

The wording intentionally remains:

> Potential Non-Compliance

---

# 49. REQUIRES_REVIEW

Human review is required because of conditions such as:

- conflict
- uncertainty
- material ambiguity
- reviewer decision requirement
- unresolved applicability

---

# 50. NOT_APPLICABLE

The requirement does not apply under the supported applicability logic.

It is not equivalent to:

```text
PASS
```

---

# 51. INCOMPLETE

The information/evidence is insufficient to complete the assessment.

Examples:

- missing required evidence
- unresolved required information
- insufficient coverage

---

# 52. PROCESSING_FAILED

A technical processing stage failed.

Examples:

- OCR service failure
- AI provider failure
- processing exception

This must never be treated as non-compliance.

---

# 53. Assessment vs Finding

An assessment answers:

> What did the rule evaluation produce?

A finding answers:

> What important condition should the user investigate/understand, and why?

Not every technical processing state needs to become a finding.

---

# 54. Finding Domain

A finding may contain:

- finding ID
- requirement
- result
- reason
- evidence
- source observation
- rule reference
- provenance
- status
- review state

---

# 55. Finding Evidence

A finding should link to relevant evidence.

```text
Finding
   ↓
Evidence
   ↓
Source Region
```

Where a finding is based on an absence/not-observed condition, the system must avoid claiming that the evidence proves universal absence unless the evidence actually establishes it.

---

# 56. Evidence-Backed Reasoning

A finding should explain:

```text
Requirement
     ↓
Observation
     ↓
Rule
     ↓
Reason
     ↓
Evidence
```

This is the domain's explainability chain.

---

# 57. Inspector Verification Domain

Inspector Verification represents human review of the system's observations.

The Inspector can:

- verify declarations
- correct extracted values
- verify applicability
- review findings
- add manual observations
- supplement evidence
- submit

---

# 58. Inspector Correction

A correction changes the current working representation of an observed fact.

The domain must preserve:

- previous value
- new value
- actor
- timestamp
- reason/source where applicable

The old value remains in history.

---

# 59. Correction Invalidation Rule

The global invariant is:

> **Upstream correction → invalidate affected downstream state → recompute → preserve prior state/history → audit transition.**

Example:

```text
MRP
System: ₹199
Inspector: ₹179
       ↓
MRP-dependent assessment invalidated
       ↓
Recalculated
       ↓
New result
       ↓
Correction history preserved
```

---

# 60. Submission Domain

Submission moves the inspection from Inspector working control to Reviewer control.

Conceptually:

```text
Inspector Verification
        ↓
SUBMITTED
        ↓
Reviewer
```

After submission, the Inspector is normally view-only unless the Reviewer requests additional evidence/correction.

---

# 61. Reviewer Domain

Reviewer is an independent operational role.

The Reviewer can:

- inspect submitted information
- inspect evidence
- inspect audit/history
- confirm assessment
- correct/override assessment
- request evidence
- finalize

The Reviewer does not need to erase or replace the system's original assessment.

---

# 62. Reviewer Decision

A Reviewer decision should preserve:

- system assessment
- Reviewer decision
- Reviewer identity
- timestamp
- reason
- related evidence/observation
- audit event

---

# 63. Reviewer Override

An override changes the decision representation while preserving the previous system assessment.

Example:

```text
System:
POTENTIAL_NON_COMPLIANCE

Reviewer:
PASS

Reason:
Additional evidence establishes compliance.
```

Both remain historically traceable.

---

# 64. Evidence Request Domain

An Evidence Request is a structured request for additional information.

It should contain:

- Evidence Request ID
- requested condition/fact
- reason
- requester
- timestamp
- status

Example:

```text
ER-00017
```

---

# 65. Evidence Request Response

The Inspector may:

```text
Add supplemental evidence
        OR
Add manual observation
        OR
State unable to establish
```

The domain must not force a particular number of images.

---

# 66. Evidence Request Reprocessing

If supplemental evidence materially changes an analyzed fact:

```text
New Evidence
     ↓
Affected Analysis
     ↓
Reprocess
     ↓
Recalculate
     ↓
Inspector Verification
     ↓
Resubmit
```

Unrelated prior results need not be unnecessarily recomputed.

---

# 67. Finalization Domain

Finalization represents the transition to protected historical state.

```text
Reviewer Decision
      ↓
Validation
      ↓
Final Snapshot
      ↓
FINALIZED
```

Finalization is not performed by AI.

---

# 68. Final Snapshot

The Final Snapshot should contain or reference:

- inspection context
- product information
- evidence references
- evidence hashes
- OCR
- AI observations
- declarations
- applicability
- assessments
- findings
- Inspector corrections
- Reviewer decisions
- rule snapshot
- provenance
- audit references
- final decision

---

# 69. Finalized Record Semantics

After finalization:

```text
Read-only historical record
```

Normal workflow edits are prohibited.

If a future correction process is ever required, it must be modeled as a separate controlled event/versioning process rather than silently mutating history.

---

# 70. Rule Snapshot Domain

Each evaluated inspection should retain the rule snapshot/version used for its assessment.

This ensures historical reproducibility.

```text
Inspection
   ↓
Rule Snapshot v1
   ↓
Assessment
```

Future rule changes must not silently recalculate finalized historical records.

---

- actor
- action
- timestamp
- target
- old/new values where relevant
- reason/source where relevant

# 74. Domain State Invariants

## Invariant 1

An AI output is not a final legal decision.

## Invariant 2

Original evidence cannot be overwritten.

## Invariant 3

Applicability precedes compliance evaluation.

## Invariant 4

Technical processing failure cannot become compliance failure.

## Invariant 5

Unsupported facts cannot become accepted declarations.

## Invariant 6

NOT_APPLICABLE is not PASS.

## Invariant 7

INCOMPLETE is not POTENTIAL_NON_COMPLIANCE.

## Invariant 8

UNREADABLE is not equivalent to NOT_OBSERVED.

## Invariant 9

CONFLICTING information is preserved.

## Invariant 10

Known affected downstream results must not remain falsely represented as current after an upstream correction.

## Invariant 11

Finalized historical records are protected from ordinary mutation.

## Invariant 12

Evidence integrity hashing does not establish truth/authenticity.

# 80. Domain Result Aggregation

An inspection may contain multiple requirement assessments.

Example:

```text
Manufacturer              PASS
Generic Name              PASS
Net Quantity              REQUIRES_REVIEW
Manufacture/Packing Date  POTENTIAL_NON_COMPLIANCE
MRP                       PASS
Consumer Care             PASS
```

The inspection-level summary should preserve the underlying requirement-level results.

A single aggregate label must not hide material requirement-level details.

---

# 81. Overall Inspection Result

The overall inspection result is derived from requirement-level state according to controlled application logic.

It must not be a free-form LLM judgment.

If material unresolved conditions exist, the result may remain:

```text
REQUIRES_REVIEW
```

If required information cannot be established:

```text
INCOMPLETE
```

If processing has failed before a meaningful assessment can be produced:

```text
PROCESSING_FAILED
```

The exact aggregation policy is governed by the rule/state specifications.

---

# 82. Domain Separation of Technical and Legal Semantics

Technical:

```text
PROCESSING_FAILED
OCR_ERROR
AI_ERROR
STORAGE_ERROR
```

Domain assessment:

```text
PASS
POTENTIAL_NON_COMPLIANCE
REQUIRES_REVIEW
NOT_APPLICABLE
INCOMPLETE
```

These layers must not be conflated.

A material domain value should indicate its source where applicable:

```text

INSPECTOR

```

The source helps establish provenance and accountability.

  ↓

# 85. Domain Treatment of AI Confidence

AI confidence is metadata about extraction/interpretation.

It does not directly determine:

```text
PASS
```

or:

```text
POTENTIAL_NON_COMPLIANCE
```

Rule evaluation must use validated structured facts and their status.

---

# 86. Domain Treatment of Evidence Confidence

Evidence sufficiency is separate from model confidence.

For example:

```text
AI confidence = High
Evidence sufficiency = Insufficient
```

This remains possible and must be represented correctly.

---

# 87. Domain Treatment of Missing Information

Missing information may produce:

```text
NOT_OBSERVED
INCOMPLETE
REQUIRES_REVIEW
```

depending on the evidence/context.

The system must not automatically conclude:

```text
Missing from OCR = Missing from package
```

---

# 88. Domain Treatment of Unreadable Information

Unreadable information may produce:

```text
UNREADABLE
```

and potentially:

```text
INCOMPLETE
```

if the requirement cannot otherwise be established.

Unreadable is not automatically:

```text
POTENTIAL_NON_COMPLIANCE
```

---

# 89. Domain Treatment of Conflicting Information

Conflicts must preserve all materially relevant values.

Example:

```text
MRP:
₹199
₹179

CONFLICTING
```

The conflict can route to Reviewer/Inspector review.

No silent merge is allowed.

---

# 90. Domain Treatment of Rule Changes

Rule changes apply to future evaluations unless an explicit controlled migration/reassessment process exists.

Finalized inspections retain:

```text
Rule Snapshot Used
```

This prevents historical drift.

---

# 91. Domain Treatment of Physical ↔ Online Verification

Target domain:

```text
Physical Product
       ↕
Online Product
```

The comparison may produce:

```text
MATCH
MISMATCH
UNABLE_TO_COMPARE
```

A mismatch is:

> Cross-Channel Inconsistency

It is not automatically a statutory violation.

This capability is outside the one-day MVP.

---

# 92. Domain Treatment of Reports

A report is an output representation of an inspection state.

For finalized inspections:

```text
Final Snapshot
      ↓
Final Report
```

The report is not the source of truth.

# 93. Domain Treatment of Dashboard Metrics

Dashboard values are derived from inspection records.

      ↓

      ↓
Metrics

Metrics must not mutate source inspection records.

# 100. Domain Model Definition of Done

# 101. Domain Anti-Patterns

Do not implement:

## AI as Legal Authority

```text
AI → final violation
```

## Boolean Declaration Model

```text
field = true/false
```

This loses uncertainty and conflicts.

## OCR-as-Truth

```text
OCR text = established legal fact
```

OCR is an observation source.

## Silent Correction

Changing data without preserving history.

## Stale Assessment

Changing a declaration while leaving dependent results unchanged.

## Mutable Finalization

Editing a finalized inspection through the normal workflow.

## Rule Drift

Recalculating historical results against newer rules without an explicit process.

# 103. Final Domain Statement

ComplianceScan models an inspection as an evidence-centered chain:

```text
Evidence
   ↓
Observation
   ↓
Declaration
   ↓
Applicability
   ↓
Assessment
   ↓
Finding
   ↓
Inspector Verification
   ↓
Reviewer Decision
   ↓
Final Snapshot
```

The domain deliberately separates:

```text
Observation
Interpretation
Applicability
Assessment
Decision
```

so that uncertainty, evidence, human verification, and historical accountability remain visible.

The governing principle is:

> **AI finds → Evidence supports → Inspector verifies → Reviewer decides.**

For the one-day MVP:

> **ONE COMPLETE DOMAIN JOURNEY > MANY PARTIAL DOMAIN FEATURES.**
